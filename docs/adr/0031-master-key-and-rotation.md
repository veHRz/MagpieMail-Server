# 0031. Master key supply, per-user root keys and rotation

- Status: Accepted
- Date: 2026-10-09
- Deciders: veHRz

## Context

ADR 0014 encrypts secrets with envelope encryption under a server master key.
S2 implements it, including `magpie admin rotate-key`, whose criterion is that
"rotating the master key re-encrypts everything without loss".

## Decision

- **Master key.**
  - 32 random bytes, base64-encoded (`magpie admin generate-key`).
  - It is provided by `MAGPIE_SECURITY__MASTER_KEY` or, preferably, by a file
    (`security.master_key_file`, such as a Docker secret). The compose stack uses
    a secret file generated by `task dev:env`: the key is then not visible in the
    container's environment.
  - `magpie serve` and `rotate-key` refuse to run without it.
  - A key is identified by a short hash, stored next to what it wraps; error
    messages never quote a key.
- **Keys.** Each user has a random 256-bit root key, wrapped by the master key in
  `user_keys`. The wrapping is bound to the user, so a wrapped key moved to
  another user does not open. HKDF-SHA256 derives two keys from the root key:
  - the data key, which seals secrets and blobs (AES-256-GCM, random nonces,
    versioned format);
  - the fingerprint key (ADR 0030).

  Every ciphertext is bound to its context (table, column, row, owner) through
  additional authenticated data: a ciphertext copied elsewhere does not open.
- **Rotation.**
  - The new key becomes `security.master_key` and the old one moves to
    `security.previous_master_keys`.
  - `magpie admin rotate-key` rewraps, in one transaction, every root key not yet
    wrapped by the current key, then records the rotation in the audit log.
  - The old key can then be removed. A rotation that cannot unwrap a key changes
    nothing.

  This is what "re-encrypting everything" means here: everything the master key
  encrypts is re-encrypted. Data sealed with the user keys does not move.
- Re-encrypting a user's data under a new root key (after the compromise of one
  user's key) is a separate operation, not built yet.

## Consequences

Rotation is fast and atomic, and needs no downtime: the server runs with both
keys during the transition. Losing the master key loses every secret and every
encrypted blob, so backups and documentation (S19) must insist on keeping it
outside the server.
