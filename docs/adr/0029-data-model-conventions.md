# 0029. Data model conventions and per-user isolation in the schema

- Status: Accepted
- Date: 2026-10-09
- Deciders: veHRz

## Context

Phase S2 lays out the data model of the whole MVP before the domains that use
it exist (S3 to S11). Several users share one database, and S3 requires that no
user can ever read another user's data.

## Decision

- One initial migration creates every MVP table: those listed by the plan, plus
  `user_keys` (ADR 0031) and `global_folder_messages`, the membership of
  messages in global folders, which the plan's list lacked.
- Identifiers are UUIDv7, generated by the server, so that an ID is known before
  the row is written (encryption binds ciphertexts to it). Timestamps are
  `timestamptz`, read in UTC.
- Every row owned by a user carries `user_id`. References between owned rows
  use composite foreign keys `(id, user_id)`: the database itself refuses to
  attach one user's message to another user's account, folder or blob.
  Repositories filter every query on the owner.
- PostgreSQL row-level security is not used for now. It needs a per-transaction
  user setting threaded through the pool, and the composite keys, the
  repositories and the cross-access tests of S3 already cover the risk. It
  remains an option for phase S19.
- Soft deletion (`deleted_at`) applies where a trash exists: messages and
  drafts. The list indexes exclude deleted rows.
- Repositories are written with their phase, once their queries are known. S2
  writes those its criteria need: users, user keys, providers, accounts
  (credentials), blob records and the audit log. Every repository is covered by
  tests on a real PostgreSQL, and CI fails below 80 % coverage
  (`task test:coverage`).

## Consequences

Later phases add queries and repositories against an existing schema. Their
schema changes are new migrations; a merged migration is never edited.
